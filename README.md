# Мониторинг доступности сайтов (acte.ru, pantis.com) → Telegram

Бесплатный мониторинг на GitHub Actions + Python, без своего сервера.
Проверка каждые ~5 минут, уведомления о падении и восстановлении в Telegram.

---

## Архитектура (коротко)

```
GitHub Actions (cron */5 * * * *)
        │
        ▼
  monitor.py  ──▶ HTTP GET сайта (статус, время ответа, контрольный текст)
        │      ──▶ TLS-проверка сертификата (срок действия)
        │      ──▶ при ошибке: 2-3 повторные попытки с паузой (защита от разового сбоя)
        ▼
  state.json  ── текущее состояние UP/DOWN каждого сайта (память между запусками)
  history.csv ── лог всех проверок (для статистики)
        │
        ▼  (если UP→DOWN или DOWN→UP)
  Telegram Bot API ──▶ сообщение в чат/канал пользователя
        │
        ▼
  git commit + push  ── state.json и history.csv коммитятся обратно в репозиторий,
                         так следующий запуск "помнит" предыдущее состояние
```

Ключевая идея хранения состояния: GitHub Actions сам по себе ничего не помнит между
запусками (каждый запуск — чистая виртуальная машина). Поэтому `state.json` и
`history.csv` коммитятся обратно в репозиторий в конце каждого запуска, а следующий
запуск при `checkout` получает их актуальную версию. Это самый простой бесплатный
способ хранить состояние без БД и без сервера.

## 0. Важно: замените контрольный текст в config.yaml

Из окружения, где готовился этот проект, не получилось напрямую загрузить
`acte.ru` и `pantis.com` (сеть песочницы заблокировала запрос к этим двум
конкретным доменам, хотя другие сайты открывались). Поэтому в [config.yaml](config.yaml)
сейчас стоят **плейсхолдеры** вместо `check_text`:

```yaml
check_text: "ЗАМЕНИТЕ_НА_РЕАЛЬНЫЙ_ТЕКСТ_С_ГЛАВНОЙ_СТРАНИЦЫ_ACTE"
```

Что сделать (1 минута на сайт):
1. Откройте https://acte.ru (и отдельно https://pantis.com) в браузере.
2. Возьмите короткий кусок текста, который точно есть на главной странице
   и не будет меняться — например часть названия компании, слоган, пункт
   меню, текст в футере. **Не берите** дату, год, "сегодня" и т.п.
3. Вставьте текст в `check_text` для соответствующего сайта.

Если оставить `check_text: ""` — проверка контрольного текста для этого
сайта просто отключится (без ошибок), но тогда мониторинг не поймает
ситуацию "HTTP 200, но фактически страница ошибки".

## 1. Как создать Telegram-бота через BotFather

1. В Telegram найдите бота **@BotFather** (официальный, с синей галочкой).
2. Отправьте ему команду `/newbot`.
3. Введите имя бота (отображаемое, любое, например `Site Monitor Bot`).
4. Введите username бота — должен заканчиваться на `bot`, например `my_site_monitor_bot`.
5. BotFather пришлёт токен вида:
   ```
   123456789:AAExampleTokenDoNotUseThisOne
   ```
   Это и есть `TELEGRAM_BOT_TOKEN`. Никому его не показывайте, это как пароль.

---

## 2. Как узнать TELEGRAM_CHAT_ID

Проще всего так:

1. Найдите в Telegram бота **@userinfobot** и нажмите Start — он покажет ваш
   личный `id` (число, например `123456789`). Это и есть `TELEGRAM_CHAT_ID`,
   если хотите получать уведомления в личку.
2. Затем откройте чат со своим только что созданным ботом (из шага 1) и
   нажмите Start / отправьте любое сообщение — боту нужно, чтобы вы написали
   ему первым, иначе он не сможет писать вам.

Альтернативный способ (без сторонних ботов), через API:
1. Напишите что-нибудь вашему боту в Telegram.
2. Откройте в браузере:
   ```
   https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates
   ```
3. В ответе (JSON) найдите `"chat":{"id":123456789, ...}` — это и есть chat_id.

Если хотите слать уведомления в **группу**: добавьте бота в группу, напишите
в группе любое сообщение, затем откройте `getUpdates` как выше — там будет
`chat_id` группы (обычно отрицательное число, например `-1001234567890`).

## 3. Куда добавить GitHub Secrets

1. Откройте ваш репозиторий на GitHub.
2. **Settings** → в левом меню **Secrets and variables** → **Actions**.
3. Кнопка **New repository secret**.
4. Добавьте два секрета:
   - Name: `TELEGRAM_BOT_TOKEN`, Value: токен от BotFather
   - Name: `TELEGRAM_CHAT_ID`, Value: ваш chat_id
5. Сохраните. Секреты не видны в логах и коде, и их не увидит даже владелец
   репозитория после сохранения (только перезаписать новым значением).

## 4. Инструкция по запуску

1. Создайте новый репозиторий на GitHub (рекомендуется **публичный** — см.
   раздел "Стоимость" ниже про лимиты Actions на приватных репозиториях).
   Название на ваше усмотрение, например `site-monitor`.
2. Скопируйте все файлы из этой папки (`site-monitor/`) в ваш локальный
   git-репозиторий и запушьте:
   ```bash
   cd site-monitor
   git init
   git add .
   git commit -m "Initial commit: site monitor"
   git branch -M main
   git remote add origin https://github.com/<ваш-логин>/<repo>.git
   git push -u origin main
   ```
3. Добавьте секреты `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID` (раздел 3 выше).
4. Замените плейсхолдеры `check_text` в `config.yaml` на реальный текст
   (раздел 0 выше), закоммитьте и запушьте изменение.
5. Откройте вкладку **Actions** в репозитории — workflow "Site monitor"
   должен появиться в списке и дальше будет запускаться сам каждые 5 минут
   по расписанию. Ждать первого автозапуска не обязательно — можно
   запустить вручную (следующий раздел).

---

## 5. Как проверить систему вручную

1. В репозитории откройте вкладку **Actions**.
2. Слева выберите workflow **Site monitor**.
3. Справа нажмите **Run workflow** (кнопка с выпадающим списком) → **Run workflow**.
4. Через 20-60 секунд запуск появится в списке — откройте его и посмотрите
   логи шага **Run monitoring check**: там видно, что проверилось, какой
   HTTP-код и время ответа получены.
5. Если всё в порядке (оба сайта доступны) — сообщений в Telegram не будет,
   это ожидаемо: уведомления шлются только при смене состояния UP↔DOWN.
6. После запуска проверьте, что в репозитории обновились файлы `state.json`
   и `history.csv` (появится новый коммит от `github-actions[bot]`).

Через терминал (если установлен [GitHub CLI](https://cli.github.com/)):
```bash
gh workflow run monitor.yml
gh run watch
```

## 6. Как специально вызвать тестовую ошибку и проверить уведомление

Самый простой способ — временно сломать один из сайтов в конфиге,
не трогая сами сайты:

**Вариант А — несуществующий адрес (DNS-ошибка):**
1. Откройте `config.yaml`, временно замените `url` для ACTE на заведомо
   несуществующий домен:
   ```yaml
   - name: "ACTE"
     url: "https://this-domain-does-not-exist-test-12345.ru"
   ```
2. Закоммитьте и запушьте, затем запустите workflow вручную (раздел 5).
3. Через 1-2 минуты (с учётом повторных попыток) в Telegram должно прийти:
   ```
   🔴 ACTE недоступен
   ...
   Ошибка: ошибка DNS (не удалось определить адрес сайта)
   ```
4. Верните `url` обратно на `https://acte.ru`, закоммитьте, запустите workflow
   ещё раз вручную — должно прийти сообщение о восстановлении:
   ```
   🟢 ACTE снова работает
   ...
   ```

**Вариант Б — неверный контрольный текст (имитация "фейковой" HTTP 200):**
1. Временно впишите в `check_text` заведомо отсутствующий на странице текст,
   например `"ЭТОГО_ТОЧНО_НЕТ_НА_СТРАНИЦЕ_12345"`.
2. Закоммитьте, запустите workflow вручную — придёт уведомление с ошибкой
   `контрольный текст не найден на странице`.
3. Верните правильный `check_text` обратно, запустите ещё раз — придёт
   уведомление о восстановлении.

**Вариант В — имитация медленного ответа:**
1. Временно поставьте в `config.yaml` `slow_response_seconds: 0.01`
   (порог ниже любого реального времени ответа).
2. Запустите workflow вручную — придёт `Ошибка: слишком медленный ответ (...)`.
3. Верните `slow_response_seconds: 5` обратно, запустите ещё раз для восстановления.

После каждого теста обязательно верните `config.yaml` в исходное состояние
и запустите workflow ещё раз, чтобы `state.json` вернулся в нормальное "UP".

## Настройки в config.yaml

| Параметр | Что значит | По умолчанию |
|---|---|---|
| `timezone` | часовой пояс для времени в сообщениях | `Europe/Moscow` |
| `request_timeout_seconds` | таймаут одного HTTP-запроса | `10` |
| `slow_response_seconds` | порог "слишком медленно" | `5` |
| `ssl_expiry_warning_days` | за сколько дней предупреждать об SSL | `14` |
| `retry_count` | всего попыток перед тревогой (включая первую) | `3` |
| `retry_interval_seconds` | пауза между попытками | `15` |
| `max_history_rows` | сколько строк истории хранить | `20000` |

## Стоимость и лимиты бесплатного тарифа

**Итоговая стоимость: 0 ₽/мес**, если репозиторий **публичный**.

- **GitHub Actions**:
  - Публичный репозиторий — минуты выполнения Actions **бесплатны без
    ограничений**. Это рекомендуемый вариант для этого проекта — в файлах
    репозитория нет ничего чувствительного (токен и chat_id хранятся
    только в зашифрованных GitHub Secrets, наружу не попадают).
  - Приватный репозиторий на бесплатном плане — **2000 минут/месяц**.
    При проверке раз в 5 минут это ≈ 288 запусков/день × ~1 минута (округление
    GitHub вверх) ≈ 288 мин/день ≈ **8600+ мин/месяц** — почти в 4 раза
    больше бесплатного лимита. То есть при приватном репозитории вы либо
    выйдете за бесплатный лимит (доплата ~$0.008/мин сверху, то есть порядка
    $50+/мес), либо нужно снижать частоту проверок (например, раз в 15-20 минут).
  - **Вывод: держите репозиторий публичным**, если хотите проверку раз в 5 минут бесплатно.
- **Telegram Bot API**: полностью бесплатен, лимитов, которые вы могли бы
  реально задеть при 2 сайтах и уведомлениях только при смене статуса, нет.
- **Хранение в git**: каждый запуск (даже без изменения статуса) дописывает
  строку в `history.csv` → это отдельный коммит каждые 5 минут, то есть
  ~288 коммитов/день. Каждый коммит крошечный, но репозиторий будет
  накапливать историю коммитов. Раз в несколько месяцев можно сделать
  "уборку" (squash истории), это не обязательно, но стоит иметь в виду.

## Слабые места такого решения

- **Точность расписания не гарантирована.** `cron` в GitHub Actions — это
  "не раньше чем", при высокой нагрузке на GitHub запуски могут задерживаться
  на несколько минут или редко пропускаться. Для мониторинга "для себя" это
  приемлемо, для SLA-критичных случаев — нет.
- **Проверка из одной точки.** Запуск идёт с раннера GitHub (обычно US),
  без проверки с разных континентов/провайдеров. Нельзя понять "сайт лежит
  для всех" или "просто эта сеть до него не достучалась".
- **Кто следит за наблюдателем?** Если у GitHub Actions сбой, лимит
  минут исчерпан, или workflow случайно отключили — мониторинг молча
  перестанет работать, и никто не пришлёт уведомление об этом самом факте.
  Это слепое пятно любого self-hosted решения без внешнего watchdog.
  Простая защита: иногда (раз в 1-2 недели) открывайте вкладку Actions
  и убеждайтесь, что запуски идут зелёные.
- **Состояние хранится через git-коммиты**, что не создано для таких частых
  записей — работает нормально при 1-2 сайтах, но не масштабируется на
  десятки сайтов с высокой частотой без пересмотра подхода (например,
  переход на внешнее хранилище).
- **Нет готового дашборда/графиков** — только `history.csv` и `state.json`
  в репозитории, для красивого отображения нужно будет что-то досчитать
  самостоятельно (например, открыть CSV в Google Sheets).
- **Только HTTP(S)-проверки** — нет ping, TCP-порт, DNS-мониторинга как
  отдельных типов проверок.
- **Один канал уведомлений** — только Telegram, без эскалации, дежурных,
  телефонных звонков/SMS.

## Насколько это хуже Better Stack / HetrixTools

Прямо — заметно хуже как "профессиональный" мониторинг, но для 2 сайтов
и личного использования разница может быть не критична:

| | Этот проект | Better Stack / HetrixTools |
|---|---|---|
| Стоимость | 0 ₽ (публичный репо) | free-тариф ограничен по числу мониторов/частоте, дальше платно |
| Минимальный интервал проверки | практически 5 мин (лимит cron) | от 30 сек — 1 мин на платных планах |
| Точность расписания | не гарантирована | SLA гарантирован |
| Точки проверки | 1 (US, GitHub-раннер) | несколько регионов на выбор |
| Дашборд / графики / uptime % | нет, нужно считать самому | есть из коробки |
| Каналы уведомлений | только Telegram (легко добавить email через тот же скрипт) | Telegram, email, SMS, звонки, Slack, PagerDuty и т.д. |
| Статус-страница для клиентов | нет | есть |
| Кто мониторит сам мониторинг | никто (слепое пятно) | у них своя отказоустойчивая инфраструктура |

Для задачи "получать пуш в Telegram, если один из двух сайтов упал"
этого решения более чем достаточно и оно бесплатно. Если понадобится
публичная статус-страница, мульти-регион или гарантии SLA — тогда уже
имеет смысл смотреть в сторону платных сервисов.
